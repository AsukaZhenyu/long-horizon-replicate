# Horizon Weaver 中文实验规划

日期：2026 年 10 月 25 日  
状态：探索阶段实验方案  
目标：检验 Task IR 对小模型长时程任务执行与 Agent 自我改进的作用

本研究考察两个问题：在相同资源下，Task IR 是否帮助 Agent 更可靠地完成长任务；从相同初始 Agent 和经验出发，Task IR 是否帮助 Agent 用更少反馈和计算获得可迁移的策略改进。主实验沿用本地小模型路线，暂以 Qwen3.5-9B Q4_K_M 为默认配置，具体权重、上下文和服务参数在运行前核实并记录。

当前先复现、观察失败、建立可计算指标，再收敛最小 Task IR。探索阶段允许调整任务族、指标和实现；用于指导调整的数据归入开发集。正式结论使用未参与设计、候选选择和调参的新实例验证。本方案没有预设 Task IR 胜出，也不把已有方法在小模型下表现差作为成立前提。

## 1 研究问题与可检验假设

| 问题 | 实验假设 | 支持它的证据 | 不能单独支持它的现象 |
| --- | --- | --- | --- |
| 执行效率 | 相同模型和预算下，结构化任务状态有助于保留进展、组织上下文并完成任务 | 正常提交且通过率提高，或同等成功率下成本降低；在长依赖任务上重复出现 | 日志更完整、组件更多、内部检查更多 |
| 改进效率 | 相同初始策略、经验和反馈下，结构使有用更新更容易被提出和保留 | 在新任务上，同改进成本获得更大收益，或更早达到同等能力 | 训练任务得分提高、提交了更多补丁 |
| 经验复用 | 学到的内容能用于不同实例，且不会大幅损害已有能力 | 同任务族新实例及新任务族上的收益，旧能力保留情况 | 同一道题反复运行后的最佳成绩 |
| 机制解释 | 收益与目标、证据、依赖、进展的表示及使用有关 | 匹配更新器和信息的表示对照、消融及可追踪的行为变化 | 仅与一个较弱手写基线比较 |

“任务内状态更新”包括记录观察、推进进度和维护当前上下文。“跨任务改进”包括持久化有用经验、改变上下文选择、修改组件与协作策略。两者分别记录。本文用 RSI 指 Agent 或 Harness 自我改进方向；若进一步声称“系统越来越善于改进自己”，需要第 8 节的独立迁移实验。

Task IR 的具体字段和执行语义仍需由复现证据约束。本方案不预先规定固定的 Planner、Critic、Verifier 等角色，也不以 JSON、图或插件形式本身作为研究贡献。

## 2 当前基础与待补能力

现有实现以 [架构文档](architecture.md) 为准。它已经提供引用与版本、上下文操作、组件执行、预算及记录等底座；现有 fixture 测试主要证明工程行为。架构文档所列的终端工具、真实任务评估、学习策略和恢复能力仍需逐项补齐，不能将它们写成已经完成的研究结果。

| 当前可利用的基础 | 实验前需要补齐的内容 |
| --- | --- |
| 不可变值、引用与执行记录 | 任务、环境、候选、模型、预算的统一配置指纹 |
| 上下文搜索、载入、保留、驱逐 | 真实 tokenizer 用量、缓存命中和每次模型请求的成本 |
| 组件执行和独立 fixture 评分 | 终端任务接入、外部 verifier 隔离、提交状态与环境快照 |
| 候选比较的工程示例 | 真正的候选生成、版本选择、回退和完整改进成本核算 |

旧 v0/v1 的八项任务只作为开发回归。历史上“整项通过”与“正常提交且通过”存在显著差异，必须保留这两个口径。旧任务、旧预算和旧运行结果不能与新版本直接拼表，详见 [历史实验总结](../history/legacy-experiments.md)。

本文件定义后续实验协议，不变更当前运行时语言和架构，也不意味着已启动模型或 benchmark。

## 3 运行单位与成功定义

### 3.1 区分四种运行单位

| 单位 | 定义 |
| --- | --- |
| 任务实例 | 固定指令、初始环境、数据和评分器版本的一项工作 |
| 任务尝试 | 从指定初始环境开始的一次自主运行；包括其内部反思、工具调用、修复和验证 |
| 候选评估 | 一个候选策略在规定任务集合上的若干任务尝试 |
| 独立改进运行 | 从共同起点重新开始，独立采集或读取经验、提出候选并选择版本的完整过程 |

重复评测同一个最终候选，不能替代重复独立改进运行。不同候选的任务尝试不能合成为一次尝试的最好结果。

### 3.2 同时记录三种结果

设一次尝试在停止时的环境为最终候选环境：

- A：artifact_pass。最终候选是否满足该 benchmark 的外部完成标准。TB 以官方整项评分为准。
- V：valid_submission。是否在预算内按预定协议正常结束并交付，未依赖人工收尾。
- Y：end_to_end_pass，定义为 A × V。

主任务成功率使用 Y，同时并列报告 A 和 V，以便与 benchmark 原生结果对照。正常退出不能代替内容正确；任务要求的 cmd.sh、async 接口、服务状态等属于交付物正确性，必须由对应任务标准检验。

| 外部结果 A | 提交状态 V | 解释 |
| --- | --- | --- |
| 1 | 1 | 完整自主完成 |
| 1 | 0 | 产物通过，但超时、崩溃或未按协议结束 |
| 0 | 1 | 正常结束，但交付错误或不完整 |
| 0 | 0 | 任务与流程均未完成 |

不额外要求 Agent 提交固定格式的“反思”或内部 verify 全绿。对官方系统，将其原生终止信号映射为 V，并公布适配规则。

预算耗尽时立即停止写操作，保存最终状态后再评分。若评分基础设施失败，可对同一不可变快照恢复原评分；不得追加 Agent 动作或人工修改候选。评分恢复不改变原来的超时、崩溃或提交状态。

对使用连续奖励的 benchmark，保留其原生奖励和完成阈值，另外说明如何映射 A；不得把若干断言通过或较高部分得分自动当作整项完成。不同 benchmark 的成功率和部分分数分表报告。

## 4 统一起点与公平比较

### 4.1 主比较共享什么

共同起点记为 H0，包含可运行的初始执行策略；D0 是可供更新方法使用的共同原始经验。主组还固定模型、工具、权限、资源、环境和反馈协议。

| 条件 | 统一办法 |
| --- | --- |
| 模型 | 固定权重及文件哈希、量化、tokenizer、推理服务版本、上下文上限、采样参数 |
| 生成角色 | 执行、压缩、反思、候选编辑、测试生成等均使用同一指定小模型；每次调用记录实际模型 |
| 初始执行策略 | 固定任务指令、基础循环、工具语义、初始上下文处理和提交协议 |
| 初始经验 | 都为空，或收到相同原始轨迹 D0；一方独有的预热技能、候选档案和专家示范另列条件 |
| 环境 | 同任务实例、容器和初始文件、网络规则、CPU/内存限制及工具可见性 |
| 反馈 | 明确区分任务描述、环境输出、公开测试、标量奖励、隐藏测试和参考答案 |
| 预算 | 使用同一成本计量与上限规则；上下文维护、无效候选及筛选也消耗预算 |
| 辅助资源 | 检索编码器、训练过的编辑器、外部服务及人工介入均列入方法配置 |

初始 Agent 应能正确调用工具、解析回复和结束任务。不要为了制造改进空间故意保留格式错误，也不要为了让初始分数相等挑选随机种子或削弱某个方法。

H0 先采用最小闭环：任务说明与当前上下文 → 一次模型决策 → 基础工具执行 → 记录观察 → 继续或提交。初始上下文规则、工具协议及错误返回方式写入共同配置，不加入针对某道题的解法。使用相同工具协议样例检查普通表示与 IR 的初始语义；具体结构在先导复现后确定。

相同初始分数不代表同起点；共享 H0 后存在采样波动也不代表起点不公平。RHO 和 RRSI 提供了共享初始 Harness 的实验参考，但它们部分比较匹配的是候选数量，需要进一步核算总计算成本。[RHO](https://arxiv.org/html/2606.05922#A6.SS4)；[RRSI](https://arxiv.org/html/2609.24972#S4.SS1)

### 4.2 分开报告三类比较

| 比较 | 改变的变量 | 允许的结论 |
| --- | --- | --- |
| 更新方法比较 | 同一可执行 H0，采用不同更新方法 | 哪种方法更有效地改进共同 Agent |
| 表示比较 | 同一初始策略分别用普通表示与 Task IR 表达，尽量保持更新方法和可用信息一致 | 表示是否改善执行或学习 |
| 原生系统比较 | 保留官方方法的核心结构、初始化和学习机制 | 整套系统在指定资源下的实际表现 |

表示对照不要求字节相同，应检查初始策略语义、信息和权限。若解释器、默认上下文或执行方式已改变初始能力，应保留这项差异并限制因果结论，不能仅减去各自初始分数就宣称完全同起点。

原生方法不全部改写到 Task IR。必要的接口迁移列入复现差异；改变更新规则、工具集或反馈来源后，应标为受控适配或论文重实现，而非官方原样复现。

### 4.3 表示与更新的四组实验

| 组别 | 表示 | 跨任务更新 | 用途 |
| --- | --- | --- | --- |
| P0 | 普通代码或文本 | 关闭 | 普通表示的固定基线 |
| P1 | 普通代码或文本 | 开启 | 普通表示下的改进 |
| I0 | Task IR | 关闭 | IR 本身的执行收益及维护成本 |
| I1 | Task IR | 开启 | IR 支持的改进 |

普通表示应包含有竞争力的普通代码或结构化记录版本，例如同信息的字段表或 JSON；原始对话和一次性摘要可作附加基线，不能是唯一对照。各组可访问的事实、原始历史与上下文预算相同，不能通过给 IR 更多信息制造收益。共同更新器获得各自表示的接口说明，适配与调参投入单列，避免一方额外获得任务解法。

关闭更新时，任务内观察、文件修改和上下文变化仍可进行；每个新任务重置为冻结的组件、策略与长期记忆。共同的只读初始经验可以保留，但不能继续写入、整理后供下一任务读取，否则仍属于学习。开启组须明确经验、组件和协作关系中的哪些部分可变。

同一表示内，关闭组应当是开启组初始化版本的冻结副本。实验同时报告四格的绝对成绩，以及更新收益的交互项：

\[
\Delta_{\mathrm{learn}}
=
[Q_{\mathrm{I1}}-Q_{\mathrm{I0}}]
-
[Q_{\mathrm{P1}}-Q_{\mathrm{P0}}].
\]

交互项用于辅助归因，不替代四格结果，也不自动排除不同表示与更新器适配程度的影响。

### 4.4 区分经验利用与经验采集

第一步给各方法相同 D0，考察它们如何组织和利用相同证据；同一批新增原始轨迹可按固定顺序提供。第二步从共同 H0 出发，在相同任务流和总预算下自行采集；之后轨迹允许不同，这是整个闭环的结果。

若比较“只读给定经验”，则所有方法禁止额外探测；若允许候选试跑，使用相同任务池和反馈权限并计费。不能一方只读日志，另一方任意调用额外 oracle。

## 5 任务集合与长时程维度

### 5.1 三层任务来源

| 层次 | 数据来源 | 用途与边界 |
| --- | --- | --- |
| 环境与协议回归 | 历史八项、极小工具任务 | 验证可运行、可提交、可评分；不承担研究收益结论 |
| 真实终端工作 | 固定版本的 Terminal-Bench；优先审查 TB 2.1 作为新的公共参照 | 跨方法真实工作比较；按软件修复、数据处理、构建部署等任务类型分层 |
| 长时程与机制诊断 | Long-Horizon-Terminal-Bench 2.0 候选任务，加受控依赖任务族 | 观察长期进展、信息保留、恢复和经验复用；与普通 TB 分表 |

TB 2.1 修复了 TB 2.0 的依赖漂移、资源与任务说明问题。选择它是为获得固定、可解释的公共参照，不代表追逐最新榜单。历史 TB、TB 2.0、TB 2.1 以及其他版本不得混分；复现论文原结果时仍保留论文对应版本。[官方修订说明](https://www.tbench.ai/news/terminal-bench-2-1)

LHTB 2.0 使用更长运行预算和过程评分检查点，适合观察“还没完全做成，但是否持续取得客观进展”。它是独立 benchmark，不是 TB 2.0 的另一个名称。接入前要核查任务资产、评分隔离与本机资源；缩短其官方预算后应标明预算受限评测，不沿用官方数字。[论文](https://arxiv.org/abs/2610.14146)

选择任务先依据环境可复现性、任务类型、依赖跨度和预算可行性。探索阶段可以依据多种方法共同出现的失败调整任务族，同时保留修订和排除理由。不得只保留有利于 Task IR 的任务。

### 5.2 长时程不能按 Agent 自己走了多少步定义

任务跨度在运行前由任务自身定义。优先使用可信的人类耗时标注；若没有，则在同一技能族内控制依赖阶段数、早期证据到使用时的距离、需要维护的中间产物和状态数量。实际工具次数和实际耗时是结果，不能反过来用于定义任务长度。

| 受控维度 | 起步方案 | 要隔离的问题 |
| --- | --- | --- |
| 依赖深度 | 同一任务生成器的短、中、长依赖链；初步可用 2、4、8 个阶段校准 | 中间结果能否保留并被后续正确使用 |
| 证据跨度 | 关键事实先出现，若干相关阶段后再次需要 | 上下文选择是否遗忘必要信息 |
| 干扰信息 | 核心任务不变，增加可辨识的无关日志或文件 | 是否重复读取、无法定位证据 |
| 可恢复中断 | 在任务定义的阶段保存环境后中断并恢复 | 能否恢复已有进展；恢复成本多少 |
| 规则变化 | 后续任务改变接口版本或环境条件 | 旧经验是否被错误复用，何时需要修订 |

上述阶段数是待校准参数，不是正式结果定义。任务链必须存在真实依赖，不能把互不相关的小任务串起来就称为长任务。任务族应包括软件工作实例，防止只证明对人工谜题有效。

过程评分使用预先定义、外部可检查的里程碑。阶段权重在观察正式结果前确定；重复达到同一里程碑不重复加分。里程碑不能全部偏向容易完成的初期准备。内部生成的计划完成度仅作日志，不作为主要进展奖励。

### 5.3 数据划分

| 集合 | 用途 | 可向谁暴露 |
| --- | --- | --- |
| 历史与探索集 | 复现、排障、形成任务族和指标 | 开发者及实验方法 |
| 更新训练集 | 采集经验、提出和改写候选 | 更新方法按协议可见 |
| 选择验证集 | 选择版本、回退和停止 | 更新方法按协议可见；调用计入学习成本 |
| 最终同分布测试集 | 测同任务族的新实例 | 仅独立评测；结果不回传更新器 |
| 最终跨分布测试集 | 测新任务族或新环境 | 仅独立评测 |

同分布测试可沿用冻结前已定义的任务族或生成器，但使用未见实例，并按原题、仓库或近重复组隔离，避免同一原题稍改路径就跨到测试集。跨分布测试进一步保留未参与设计的任务族或环境；两者分别报告，不能把所有测试都换生成器后仍称为同分布。由观察过的失败定向构造的变体属于开发数据。

测试快照在复制出的环境和只读策略版本上评测，关闭跨任务写回。即使正式测试只返回分数，若据此改算法或挑版本，也已变成开发反馈，需要新的确认数据。

## 6 成本计量

### 6.1 本地成本与 API 成本分别记录

本地单卡主组固定硬件、服务版本及并发。优先记录可归因的推理计算时间；若无法可靠测量 GPU 活跃时间，则在单请求、无并发干扰条件下记录模型服务请求耗时，并明确它只是代理指标。不能把请求耗时直接标成真实 GPU 计算时间。

每次调用记录输入 token、缓存命中 token、输出 token、模型服务耗时；每个任务记录 Agent 端到端时间、工具时间、容器准备、评分及清理时间。输入和输出 token 不假定单位成本相同。API 组另按记录的实际价格计算费用，不把美元、秒和 token 直接相加。

实验预算 B 由模型计算预算及固定的墙钟、上下文、工具调用保护上限组成。预算曲线一次只变化一个主要预算轴；记录每次由哪一项上限终止，防止实际比较的是不同瓶颈。

### 6.2 执行与改进分别记账

- 执行成本：本次任务内的全部模型调用、上下文操作、内置反思、自生成测试和工具执行成本；成功和失败都记录。
- 改进成本：经验采集、候选初始化、反思/提案、编辑、全部候选试跑、验证选择、失败和回退的成本。
- 独立测量成本：研究者为报告曲线、置信区间和最终泛化而进行的评分，单独记录；若结果参与版本选择，该部分就属于改进成本。
- 预训练或强模型辅助：单列训练数据、模型来源及可获得的训练/构建成本；不知道的成本标未知，不填写零。

共享 D0 的原始采集成本作为共同前置成本单列。条件学习曲线从各方法拿到同一 D0 开始计费，编码、压缩、建图、初始化候选池的成本都从此处累计；另报告含共同采集成本的端到端总账。空经验在线实验中，采集成本直接进入学习曲线。

C=0 使用共同初始版本及原始、未做方法专属加工的 D0。方法专属预处理只有完成后才能使用，其成本对应正的 C。可复用的建图、压缩或索引计入改进成本；每次执行时临时构造上下文计入该次执行预算。同一工作不能免费，也不能重复入账。

所有预算超支采用同一规则：不启动预计无法容纳的请求；正在执行的请求按预定超时处理，并记录实际超支。硬上限之外才完成的提交令 V=0；取消与计时容差如有必要，须预先固定并同等应用。改进预算截止前尚未完成选择的候选，不得计入该检查点的已采用版本。

## 7 定量指标

### 7.1 任务完成效率

设任务 i 在预算 B 下的完整完成结果为 Y_i(B)，所有尝试的实际执行成本为 c_i。

| 主指标 | 定义 | 解释 |
| --- | --- | --- |
| 预算成功率曲线 | S(B) = 平均 Y_i(B) | 相同资源下完成多少任务 |
| 每成功任务成本 | CoP = Σc_i / ΣY_i | 获得一个完整成功的实际投入 |

两项并报，并按任务类型与预先定义的跨度 h 展示 S(B,h)。CoP 的分子包括失败与重试；零成功时记为不可估计或无穷，不填零。另报以 A 为分母的原生 benchmark CoP，并明确标签。

预算点先在开发集校准，再选择如 0.5B0、B0、2B0 的档位。每个预算点原则上独立运行，因为预算会影响规划、验证和退出。从一次长运行中截取快照只能形成“同一运行的过程曲线”，不能冒充独立预算下的完成率。

不默认 best-of-k。主表是一项任务在给定预算中的最终交付；若允许多次候选或重试，必须由 Agent 使用协议允许的反馈选择提交结果，所有尝试计费。依赖隐藏 oracle 选择的 pass@k 仅作为不同协议的辅助结果。

### 7.2 自我改进效率

设累计改进成本为 C，版本 H(C) 由训练和选择验证反馈确定。固定任务执行预算 B0，在新任务上评估得到：

\[
Q(C)=S_{\mathrm{test}}(H(C), B_0).
\]

| 主指标 | 定义 | 解释 |
| --- | --- | --- |
| 改进成本能力曲线 | Q(C)，并列初始 Q(0) 及绝对增益 | 相同学习投入后能完成多少新任务 |
| 平均改进收益 | 下面的 AUC_gain | 是否较早获得、持续保留改进 |

\[
\mathrm{AUC}_{\mathrm{gain}}
=
\frac{1}{C_{\max}}
\int_0^{C_{\max}}\left[Q(C)-Q(0)\right]\mathrm{d}C.
\]

所有方法使用相同 C_max 和预定测量规则。初期使用 0、0.5C_max、C_max 三个预算检查点，正式实验宜增加检查点。到检查点时保存当前已采用的完整版本；若没有新版本则沿用父版本，但已花费的搜索成本仍累计。以左端点保持估计面积：

\[
\widehat{\mathrm{AUC}}_{\mathrm{gain}}
=\frac{1}{C_{\max}}
\sum_{j=0}^{m-1}(C_{j+1}-C_j)[Q(C_j)-Q(0)].
\]

该估计只反映已测检查点，不补画“最佳时刻”或强制单调曲线。只有三个检查点时，终点增益不会进入上述面积，因此必须并报最终 Q(C_max)；不能声称稀疏测量完整捕捉了中途改进与退化。

检查点按花费预算对齐，不按迭代轮数或候选数对齐。正式测试可以在更新过程完成后统一对保存的检查点测量，避免结果回流。原生在线学习协议另列，不能将“测试中还在更新”的结果当作冻结版本测试。

同时以累计原始任务数、任务尝试数绘制能力曲线，以区分样本效率和计算效率。可补充达到共同能力阈值所需成本 C_tau；未达到则报告“预算内未达到”，并报告估计不确定性。

不同起点间，AUC_gain 只能描述各自的提升，不能消除先验差异。比较表示时还需结合第 4 节的四组结果。

### 7.3 长期稳定性与机制诊断

| 指标 | 可计算口径 | 注意事项 |
| --- | --- | --- |
| 外部产物通过率与正常提交率 | 平均 A、平均 V，与平均 Y 并列 | 防止把收尾失败误认为全部解题失败 |
| 无效重复成本占比 | 同一相关状态和前提下，重复已有无效尝试的成本 / 总执行成本 | 命令相同不是充分条件；修复后重跑测试、等待异步结果不自动算重复 |
| 恢复成功率与额外成本 | 从同一任务阶段注入相同中断，相对于配对无中断运行的结果与成本 | 区分仅上下文丢失、进程重启和环境恢复；不假定 Docker 可恢复任意外部副作用 |
| 客观进展曲线 | 外部里程碑得分随时间/成本变化 | 不由 Agent 自评；保持评分不影响原环境与 Agent |
| 退化与新增成功 | 同一评测面板中，更新前成功后失败，以及更新前失败后成功的比例 | 两项都报，分母固定；重复评估区分随机波动 |
| 内部验证可靠性 | 内部“完成”判断与最终外部结果的混淆矩阵 | 有内部判断才计算；没有判断不是零误差 |
| 更新与复用情况 | 候选生成/可执行/采用比例，组件实际调用或上下文暴露事件 | 仅作机制诊断；引用存在不等于产生因果收益 |

重复检测先用可审计规则，例如相同动作、相关文件/环境版本相同、观察结果相同。模糊语义重复另行人工抽查，报告覆盖率；不要求额外强模型成为主指标的裁判。

可补充部署总账：
总摊销 CoP =（共同数据成本 + 初始化与改进成本 + 固定后续任务流的执行成本）/ 该任务流的成功数。
它需要固定部署任务流规模并与成功率同时报告，不预设迭代一定回本。

## 8 具体实验

| 编号 | 实验 | 固定条件与变化 | 必须产出的结果 |
| --- | --- | --- | --- |
| E0 | 官方流程与本地接口复现 | 先保留原机制，必要时迁移所有生成角色到本地模型 | 资产/接口清单、运行证据、方法特征是否实际生效、复现差异 |
| E1 | 固定策略的任务效率 | 固定策略和长期记忆，改变预算与任务跨度 | S(B,h)、CoP、A/V/Y、完整失败记录 |
| E2 | 相同经验下的表示与更新对照 | 共享 H0 语义、D0、更新器和反馈；进行 P0/P1/I0/I1 | 四格结果、初始差异、学习交互项、表示维护成本 |
| E3 | 完整自我改进闭环 | 同起点、任务流与成本上限；各自产生经验 | Q(C)、AUC_gain、样本效率、退化与转移 |
| E4 | 改进策略的迁移 | 保留学到的改进器，执行器重置为新域共同 H0 | 相同预算内能否更快改进新 Agent |
| E5 | 扰动与消融 | 在确认有效的方法上逐项移除机制或注入受控中断 | 收益来源、恢复边界、运行时开销 |

E4 是扩展实验：只有实现确实学习了改进策略，才开展。只保存更好的执行组件不能支持“改进器本身变强”的结论。HyperAgents 的 imp@k 为这一问题提供参考；本研究还需固定新域执行器起点，并用总成本代替单纯候选数量。[HyperAgents](https://arxiv.org/html/2603.19461v1#S5.SS2)

E3 必须有两类朴素基线：完全不跨任务学习的固定 Agent，以及将相同额外资源用于直接多次尝试/顺序修订的 Agent。后者按相同反馈权限选择最终交付。比较摊销收益时固定后续任务流规模，避免为 RSI 任意增加部署任务数。[预算与反馈控制研究](https://arxiv.org/abs/2607.12227)

E5 优先回答实际观察到的问题，如去掉依赖信息、以无结构摘要替代状态表示、保留同一经验但改变检索时机、禁止跨任务复用。除被研究变量外尽量保留信息和预算。不要为了好看的消融结果故意剥夺对照必要输入。

- [Harness Self-Evolution 阅读清单](https://github.com/zgcagi/Harness-RSI)：持续扩展候选时使用的索引；具体机制和结果回到原论文核验。

记录应足以从原始文件重新计算指标，避免汇总表依赖人工记忆。以下是待实现的文件约定，不代表已经存在的运行产物。

| trials.jsonl | 任务与随机种子、策略版本、预算、退出状态、A/V/Y、成本与最终环境引用 |
| candidates.jsonl | 父候选、修改对象、源码差异、提出/评估成本、合法性、采用/回退原因 |

| scores.jsonl | 独立外部评分、错误分类、评分恢复来源和评分器版本 |
| summary.csv | 由固定脚本派生的结果；保留分子、分母和单位 |
| reproduction_notes.md | 官方配置、实际适配、缺失资产、机制生效证据及已知限制 |

实验 ID、任务实例、完整改进运行、候选和单次尝试使用不同标识。每个子调用关联父调用；一次任务或候选的成本只入账一次，避免父级汇总加子级明细造成重复计费。

基准测试文件和参考解不进入 Agent 可访问目录。测试进程不修改学习状态；凭证不写入公开轨迹。日志可以保留实际提示与工具输出的可审计引用，发布时检查个人数据和服务凭证。

## 11 统计与故障处理

1. 所有方法在相同任务实例上成对比较。先计算每任务跨重复的结果，再计算总体或任务族宏平均；不得因某方法多跑了几次就改变任务权重。
2. 执行实验初筛可单次运行；关键对比至少安排多个随机种子。正式 RSI 尽量使用至少三次从 H0 重启的独立改进运行，并改变配对任务顺序。三次只是可行起点，不保证统计充分。
3. 区间估计保留任务族、任务和改进运行的层次。可用配对分层重采样；不能把同一任务的多条轨迹当成独立新任务，也不能把同一学习曲线的检查点当独立样本。
4. 同时报绝对分数、百分点差、成本和区间。CoP 的区间重算分子与分母，零成功的重采样结果不得静默删除。
5. 初期根据先导方差及希望识别的最小实际收益估算样本量。若区间仍很宽，应报告证据不足；不以某次有利结果决定停止。
6. 预先定义基础设施错误：任务启动前环境不可用、外部评分器崩溃等。Agent 导致的依赖破坏、超时、解析失败和运行时契约错误属于系统结果，不能一律剔除。
7. 外部无效任务按相同规则对各方法处理，公布原计划数量、有效数量及错误率；必要时成对重跑，保留原记录。不只重跑失败的方法并保留最好结果。
8. 选择版本只能使用选择验证集。最终测试不选最佳 checkpoint；预先指定的检查点全部报告，并允许出现能力下降。
9. 若只有八项任务或一次改进运行，结论限于工程验证和案例分析，不写成总体优越性。

## 12 分阶段安排与成本上限

### 12.1 先小规模发现问题，再扩大确认

| 阶段 | 工作 | 建议起步规模 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| P0 环境与口径 | 评分隔离、提交映射、完整成本、官方机制与本地接口 | 每个首批方法 1 至 2 个原生任务，加历史回归 | 成功与失败均可记录、重算，核心机制确实执行 |
| P1 共同执行基线 | 建立 H0；小模型协议与任务跨度校准 | 12 个探索任务，覆盖短中长；先 3 个执行配置各 1 次 | 能区分任务、接口、环境失败；得到时间与成本分布 |
| P2 小规模学习闭环 | 相同 D0 的表示对照和少量在线更新 | 2 种表示，2 次独立更新运行；诊断面板使用开发任务 | 更新、拒绝、回退和复用均可观察；成本与评估不回流 |
| P3 机制收敛 | 针对共同失败确定最小 IR 与必要消融 | 优先复测关键配对，逐步加入 A/B 批对照 | 明确结构假设、最强开发基线和正式协议 |
| P4 独立确认 | 冻结方法/协议，对新实例和新任务族测量 | 下述预算样例起步，按不确定性扩充 | 结果可重复；报告全部负面证据和适用范围 |
| P5 扩展 | 更长任务、服务器数据、更广模型或改进器迁移 | 根据已经成立的主要结果分配资源 | 不影响主实验的可复现性和边界 |

P1 的单预算起步为 12 × 3 = 36 次任务尝试。若同样规模增加到三个预算点，则是 108 次；每个预算点需要独立运行。初筛不能代替最后的重复确认。

### 12.2 正式学习曲线的预算样例

以下仅用于规划计算量，不是已确定数据划分，也不意味着该样本量足以发表。

假设比较两种表示，每种都有开启/关闭更新；选择合计 24 个新测试任务、3 次独立改进运行，以及 0、中点、终点三个检查点。同分布与跨分布的数量分别写入 manifest；以下 24 个是两者合计：

- 两种表示的初始/冻结版本评测：2 × 24 × 3 = 144 次。
- 两种开启更新的表示，在中点和终点评测：2 × 2 × 24 × 3 = 288 次。
- 合计 432 次外部评测尝试；尚不含训练采集、候选筛选、消融与官方系统对照。
- 若扩到 48 个测试任务，同样配置为 864 次。

初始/冻结测量仅在策略、长期记忆、环境、预算完全相同的条件下复用。同一任务、同一改进运行和复用基线造成的统计相关性需要保留；432 次不是 432 个统计独立样本。若同分布和跨分布各选 24 个任务，则合计 48 个，预算为 864 次。

若每次尝试平均占用 10 分钟端到端时间，432 次约为 72 个串行小时，仅作算术示例。实际排期使用 P1 的测量，并另估模型推理、工具、环境准备、外部评测和候选搜索开销，不能把 72 小时称为 GPU 时间。

本地先以单并发建立稳定计量。服务器阶段用于扩大训练经验、独立更新运行和新任务覆盖，避免主实验切换硬件后只比较墙钟时间。额外 API 不默认启用；如需要强模型作为上界或改进器参考，应单列实验条件和费用上限。

## 13 论文结果需要回答什么

| 图表 | 主要内容 | 可支持的判断 |
| --- | --- | --- |
| 执行主表 | 模型、任务数、预算、A/V/Y、CoP、成本单位 | 能否在有限预算下完整交付 |
| 执行曲线 | S(B,h)，按真实任务与受控任务族分开 | 增加资源是否持续有用，任务变长后是否稳定 |
| 学习主图 | 同起点 Q(C)、初始能力、AUC_gain 与区间 | 是否更高效地从反馈获得新任务能力 |
| 四组对照表 | P0/P1/I0/I1 与交互项 | 架构直接收益和学习收益的区别 |
| 泛化与保留表 | 新实例、新任务族、原有能力退化 | 改进能否复用，代价是什么 |
| 机制与总账 | 重复成本、恢复、实际经验使用、完整搜索成本 | 为什么有效，以及使用多少次才可能值得投入 |

接受并报告以下可能结果：

- IR 仅改善零样本执行：支持执行结构贡献，不能声称提高 RSI 效率。
- IR 仅降低维护或搜索开销：在同等能力证据成立时支持效率贡献。
- 训练任务改善、测试任务不改善：说明泛化不足，需要检查经验或选择偏差。
- 只在强改进器帮助下有效：限定为强模型辅助构建小模型策略，不能称为全小模型自改进。
- 图或代码表示本身没有稳定差异：重新审视表示假设，保留可复现的负面结果。
- 初期有提升但后续退化：报告完整曲线，研究更新接受和经验适用边界。

正式论文不以“Task IR 胜过所有 Agent”作为目标。核心证据是：在清楚定义的同起点、同反馈、同资源条件下，这种结构是否改善长期执行或经验到策略的转化效率，以及这种收益何时成立。
